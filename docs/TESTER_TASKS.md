# Задачи для тестировщика по веткам

Формат — тест-кейс на PR: контекст, доступы, шаги, **ожидаемый результат
для каждого шага** (взят из базового поведения системы, см.
`docs/DESIGN.md`, раздел «Сценарий 0 — Baseline»), поле для фактического
результата и вывода. Ожидаемый результат — это то, что должно происходить
по спеке; несовпадение с фактическим — то, что находит тестировщик сам,
методом из `docs/KAFKA_TESTING_THEORY.md`, раздел 12 (сравнить «сколько
сообщений» с «сколько результата»).

## Доступы (общие для обеих задач)

- Swagger `order-api`: `http://<host>:8000/docs`
- Kafka UI: `http://<host>:8081`
- Kibana: `http://<host>:5601` (индекс `app-logs-*`, поле времени `@timestamp`)
- Postgres (DBeaver): `<host>:5432`, база `orders_db`, пользователь
  `orders_user`, пароль `orders_password`

`<host>` — адрес стенда ведущего (даётся в чате занятия).

## Задача 1: PR `feature/producer-bugs`

**Контекст.** В ветку `feature/producer-bugs` внесены изменения в
`order-api`: добавлен быстрый путь для части переходов статуса заказа и
логирование в ручке массовой рассылки (`dispatch-batch`). PR открыт в
`main`, CI (линт + юнит-тесты) — зелёный.

**Что проверяем на каждом шаге.** Что вернула HTTP-ручка (Swagger); что
реально попало в Kafka (Kafka UI → топик → количество сообщений и
содержимое, вкладка Value); что получилось на выходе
(`GET /orders/{id}/delivery`, таблица `deliveries` в DBeaver); что видно
в логах (Kibana, поиск по `correlationId` = id заказа).

### Сценарий 1 — обычный переход статуса

**Действие:** создать заказ (`POST /orders`), затем
`PATCH .../status` → `IN_PROGRESS`, затем `PATCH .../status` →
`READY_FOR_DELIVERY`.

**Ожидаемый результат:**
- в топике `order.status_changed` — **ровно 1** сообщение с этим
  `correlationId`, содержащее `correlationId`, `orderId`, `eventType`,
  `status`, `occurredAt`;
- `GET /orders/{id}/delivery` возвращает запись со `scheduled_at` ≈
  `occurredAt` + 2 дня (не 404).

**Фактический результат / вывод:** _заполняет тестировщик_.

### Сценарий 2 — переход напрямую, минуя `IN_PROGRESS`

**Действие:** создать ещё один заказ и сразу перевести его из `NEW` в
`READY_FOR_DELIVERY` одним вызовом `PATCH .../status`.

**Ожидаемый результат:** то же самое, что и в сценарии 1 — переход в
`READY_FOR_DELIVERY` штатно обрабатывается системой независимо от того,
из какого статуса он произошёл:
- **ровно 1** сообщение в `order.status_changed`, содержащее все те же
  поля (`orderId` в том числе);
- `GET /orders/{id}/delivery` возвращает запись, а не 404.

**Фактический результат / вывод:** _заполняет тестировщик_.

### Сценарий 3 — массовая рассылка (`dispatch-batch`)

**Действие:** через DBeaver посчитать `SELECT count(*) FROM orders WHERE
status = 'READY_FOR_DELIVERY'` — назовём число **N**. Затем вызвать
`POST /orders/dispatch-batch`.

**Ожидаемый результат:**
- ответ ручки: `dispatchedCount` равен **N**;
- в топике `order.dispatch_requested` появляется ровно **N** новых
  сообщений (по одному на каждый из этих заказов);
- в таблице `deliveries` появляется ровно **N** новых записей (для
  заказов, у которых её ещё не было).

Все три числа (ответ ручки, число сообщений в Kafka, число новых записей
в БД) должны совпадать между собой и с **N**.

**Фактический результат / вывод:** _заполняет тестировщик_.

**Как фиксировать результат.** Для каждого сценария, где факт разошёлся
с ожиданием — зафиксировать: номер заказа, `correlationId`, что
ожидалось, что получилось по факту, ссылка/скриншот-подтверждение
(Kafka UI / Kibana / DBeaver). Если по какому-то сценарию расхождений
нет — зафиксировать и это («сценарий 1: соответствует ожиданиям»).

## Задача 2: PR `feature/consumer-bug`

**Контекст.** В ветку `feature/consumer-bug` внесено изменение в
`delivery-worker`: другая стратегия коммита offset'а (реже, батчами,
ради снижения нагрузки на брокер). PR открыт в `main`, CI — зелёный.

**Что проверяем.** Устойчивость к передеплою/рестарту воркера — сравнение
состояния «до» и «после» рестарта.

### Шаг 1 — довести заказ до доставки

**Действие:** создать заказ, провести штатно до `READY_FOR_DELIVERY`
(через `IN_PROGRESS`).

**Ожидаемый результат:**
- в Kafka UI, топик `order.status_changed` — **ровно 1** сообщение с
  этим `correlationId`;
- в таблице `deliveries` — **ровно 1** запись для этого заказа.

**Фактический результат:** _заполняет тестировщик_ (запиши оба числа —
пригодятся для сравнения на шаге 3).

### Шаг 2 — имитация передеплоя

**Действие:** попросить ведущего выполнить рестарт `delivery-worker`
вскоре после шага 1.

**Ожидаемый результат:** рестарт консьюмера сам по себе не публикует и
не удаляет сообщения — количество сообщений в Kafka для этого
`correlationId` не должно измениться по сравнению с шагом 1.

### Шаг 3 — повторная проверка после рестарта

**Действие:** снова проверить Kafka UI (топик `order.status_changed`,
тот же `correlationId`) и таблицу `deliveries` для того же заказа.

**Ожидаемый результат:**
- число сообщений в Kafka — **то же, что и на шаге 1** (не выросло —
  продюсер в этой ветке не менялся);
- число записей в `deliveries` для этого заказа — **тоже 1, как и на
  шаге 1** (не выросло).

**Фактический результат / вывод:** _заполняет тестировщик_. Если записей
в `deliveries` стало больше, а сообщений в Kafka — нет, это значит, что
одно и то же сообщение было обработано более одного раза — то есть
причина на стороне консьюмера (`delivery-worker`), а не продюсера
(`order-api`, который в этой ветке не менялся).

**Как фиксировать результат.** id заказа, `correlationId`, число
сообщений в Kafka на шаге 1 и на шаге 3, число записей в `deliveries` на
шаге 1 и на шаге 3, вывод (совпадает с ожиданием / расходится и как
именно).

## Подсказка (использовать, если совсем не двигается)

Правило из `docs/LESSON_PLAN.md`: если сообщений в Kafka меньше или
столько же, сколько ожидалось, а результата нет/меньше — смотреть на
консьюмера; если сообщений больше одного на действие — смотреть на
продюсера.

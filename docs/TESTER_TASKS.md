# Задачи для тестировщика по веткам

Формат — как настоящий тест-таск на PR: контекст, доступы, что
тестировать, как фиксировать результат. Специально не сказано «здесь
баг(и)» — это находит тестировщик сам, методом из
`docs/KAFKA_TESTING_THEORY.md`, раздел 12 (сравнить «сколько сообщений» с
«сколько результата»).

## Доступы (общие для обеих задач)

- Swagger `order-api`: `http://<host>:8000/docs`
- Kafka UI: `http://<host>:8081`
- Kibana: `http://<host>:5601` (индекс `app-logs-*`, поле времени `@timestamp`)
- Postgres (DBeaver): `<host>:5432`, база `orders_db`, пользователь
  `orders_user`, пароль `orders_password`

`<host>` — адрес стенда ведущего (даётся в чате занятия).

## Задача 1: PR `feature/producer-bugs`

**Контекст.** В ветку `feature/producer-bugs` внесены изменения в
`order-api`: добавлен быстрый путь для части переходов статуса заказа и
логирование в ручке массовой рассылки (`dispatch-batch`). PR открыт в
`main`, CI (линт + юнит-тесты) — зелёный.

**Что нужно проверить.** Полный цикл заказа и оба сценария смены статуса,
плюс массовую рассылку. Для каждого сценария сравнивай:
1. Что вернула HTTP-ручка (Swagger).
2. Что реально попало в Kafka (Kafka UI → топик → количество сообщений и
   их содержимое, вкладка Value).
3. Что получилось на выходе (`GET /orders/{id}/delivery`, таблица
   `deliveries` в DBeaver).
4. Что видно в логах (Kibana, поиск по `correlationId` = id заказа).

**Сценарии:**

1. Создать заказ (`POST /orders`), провести его штатно:
   `PATCH .../status` → `IN_PROGRESS`, затем `PATCH .../status` →
   `READY_FOR_DELIVERY`. Сверить количество сообщений в топике
   `order.status_changed` для этого заказа с ожидаемым.

2. Создать ещё один заказ и перевести его сразу из `NEW` в
   `READY_FOR_DELIVERY`, минуя `IN_PROGRESS`. Сверить: появилось ли
   сообщение, корректно ли оно (все ожидаемые поля на месте), появилась
   ли запись о доставке.

3. Выполнить `POST /orders/dispatch-batch`. Заранее посчитать (через
   DBeaver), сколько заказов реально в статусе `READY_FOR_DELIVERY`.
   Сравнить с числом в ответе ручки (`dispatchedCount`) и с реальным
   числом новых сообщений в топике `order.dispatch_requested` за этот
   вызов.

**Как фиксировать результат.** Для каждого расхождения между «ожидалось»
и «получилось» — зафиксировать: номер заказа, `correlationId`,
сценарий, что ожидалось, что получилось, ссылка/скриншот на
подтверждение (Kafka UI / Kibana / DBeaver). Если расхождений не найдено
в каком-то сценарии — тоже зафиксировать («сценарий 1: соответствует
ожиданиям»).

## Задача 2: PR `feature/consumer-bug`

**Контекст.** В ветку `feature/consumer-bug` внесено изменение в
`delivery-worker`: используется другая стратегия коммита offset'а
(реже, батчами, ради снижения нагрузки на брокер). PR открыт в `main`,
CI — зелёный.

**Что нужно проверить.** Устойчивость к передеплою/рестарту воркера.

**Сценарий:**

1. Создать заказ, провести его до `READY_FOR_DELIVERY` (штатный переход
   через `IN_PROGRESS`). Убедиться, что в Kafka UI по топику
   `order.status_changed` для этого заказа ровно одно сообщение, и что
   появилась ровно одна запись в `deliveries` для этого заказа (DBeaver).

2. Попросить ведущего выполнить рестарт `delivery-worker` (имитация
   передеплоя) вскоре после шага 1.

3. После рестарта — снова проверить: сколько сообщений в Kafka UI для
   этого `correlationId` (должно быть по-прежнему то же число, что и в
   шаге 1 — рестарт консьюмера не создаёт новых сообщений в топике,
   меняется только то, что и сколько раз обработано), и сколько записей
   в `deliveries` для этого заказа теперь.

**Как фиксировать результат.** Сравнить количество сообщений в Kafka UI
(шаг 1 vs шаг 3 — должно совпадать, это ответственность продюсера,
который тут не менялся) с количеством записей в `deliveries` (шаг 1 vs
шаг 3 — если выросло без нового сообщения в Kafka, это симптом на
стороне консьюмера). Зафиксировать: id заказа, `correlationId`, число
сообщений в Kafka до/после, число записей в `deliveries` до/после,
вывод.

## Подсказка (использовать, если совсем не двигается)

Правило из `docs/LESSON_PLAN.md`: если сообщений в Kafka меньше или
столько же, сколько ожидалось, а результата нет/меньше — смотреть на
консьюмера; если сообщений больше одного на действие — смотреть на
продюсера.

# Дизайн: учебный стенд Kafka + CI/CD (order-delivery-kafka-lab)

Дата: 2026-09-13
Статус: дизайн согласован в брейнсторминге, ждёт перехода в план реализации.

## 1. Цель

Одно занятие (1–1.5 часа) для живой когорты QA-студентов, живьём по Zoom.
Ведущий выступает «разработчиком», студенты — «QA»: тестируют ветки с уже
заложенными багами через общий стенд. Занятие должно раскрыть одновременно:

- **Kafka** — роли продюсера/консьюмера, типичные баги (дубли, битые
  сообщения, потери в батче, повторная обработка) и то, как их диагностируют.
- **CI/CD** — реальный пайплайн (GitHub Actions), что он проверяет и почему
  зелёный чек ничего не говорит о поведении на границе с Kafka.
- Полный рабочий цикл: **push → CI → checkout → ретест → фикс → ретест**.

Репозиторий полностью самостоятельный — не разделяет код, docker-сети или
историю с продуктовым TaskFlow-курсом.

## 2. Бизнes-сценарий и ручки

Мини-сервис доставки заказов, два процесса:

- **`order-api`** (продюсер, HTTP API):
  - `POST /orders` — создать заказ.
  - `PATCH /orders/{id}/status` — сменить статус; при переходе в
    `READY_FOR_DELIVERY` публикует событие в топик `order.status_changed`.
  - `GET /orders/{id}/delivery` — посмотреть назначенную дату/время
    доставки (результат работы консьюмера) — для верификации.
  - `POST /orders/dispatch-batch` — найти все заказы в статусе
    `READY_FOR_DELIVERY` и разослать по одному событию на каждый в топик
    `order.dispatch_requested`. Возвращает `{dispatchedCount: N}`.
- **`delivery-worker`** (консьюмер): подписан на `order.status_changed` и
  `order.dispatch_requested`, назначает дату/время доставки, пишет запись в
  таблицу `deliveries`.

Каждое событие несёт `correlationId` (= `orderId`), сквозной по логам и по
Kafka-сообщению — это ключ для всей диагностики в занятии.

## 3. Инфраструктура

Один `docker-compose.yml`, поднимается заранее (до начала созвона — ELK
стартует не быстро, дорого рисковать этим при студентах):

- Kafka (KRaft-режим, без Zookeeper), один брокер, по одной партиции на
  топик — порядок сообщений детерминирован, как в тренировочном стенде
  публичного курса.
- Kafka UI.
- Postgres (`orders`, `deliveries`).
- ELK (Elasticsearch + Kibana + Filebeat) — `order-api` и `delivery-worker`
  пишут структурированные JSON-логи с `correlationId`, Filebeat забирает их
  в Elasticsearch, поиск — через Kibana.

### Данные

При старте контейнеров автоматически сидируется ~12–15 заказов в разных
статусах (`NEW`, `IN_PROGRESS`, несколько `READY_FOR_DELIVERY`, немного
`DELIVERED`) — чтобы батч-ручке и общей демонстрации было на чём работать,
а не только на том, что создано вручную во время занятия. Один из
seed-заказов в `READY_FOR_DELIVERY` намеренно имеет граничные данные
(см. Баг 3) для срабатывания бага в батче.

Дополнительно — `POST /admin/reset` (не для студентов, только для
собственных прогонов/репетиций ведущего): пересоздаёт БД с тем же сидом.

## 4. Сценарии и баги

Общий приём диагностики во всех случаях: сравнить «сколько сообщений в
Kafka UI» с «сколько результатов на выходе» (в API/БД/Kibana).

### Сценарий 0 — Baseline (на `main`, без багов)

Демонстрация полного цикла и всех 4 инструментов (Swagger, Kafka UI,
Kibana, DBeaver): создать заказ → сменить статус → 1 сообщение в Kafka UI
→ 1 запись в `deliveries` → видно через `GET /orders/{id}/delivery`.

### Ветка `feature/producer-bugs` (3 бага)

1. **Дубль сообщения.** Одна смена статуса → 2 одинаковых сообщения в
   `order.status_changed` (наивная retry-логика без идемпотентности:
   повторная публикация не проверяет, прошла ли первая).
2. **Битое сообщение.** При определённом переходе статуса публикуется
   событие с некорректными данными (отсутствует обязательное поле/неверный
   тип). Kafka это спокойно хранит — не валидирует схему. `delivery-worker`
   не может распарсить, ловит исключение, логирует ошибку (видно в Kibana
   по `correlationId`) и коммитит оффсет дальше — доставка не создаётся,
   вызывающий получил 200 OK на исходный `PATCH`.
3. **Неполный батч.** `dispatch-batch` находит N заказов в
   `READY_FOR_DELIVERY`, но на одном (заранее заложенном граничном) заказе
   падает в цикле и тихо пропускает его (голый `except`), при этом отвечает
   `dispatchedCount: N` (посчитано по запросу к БД, а не по факту
   отправленных). Расхождение видно только сверив
   `SELECT count(*) FROM orders WHERE status = 'READY_FOR_DELIVERY'` (через
   DBeaver) с реальным числом сообщений в топике `order.dispatch_requested`.

Один подготовленный fix-коммит закрывает все 3 бага разом — для ретеста.

### Ветка `feature/consumer-bug` (1 баг)

4. **Повторная обработка.** Ровно 1 сообщение в Kafka UI, но
   `delivery-worker` не отслеживает уже обработанные события и/или
   коммитит оффсет некорректно (до завершения записи в БД, либо теряет
   позицию консьюмер-группы). После рестарта контейнера воркера
   (имитация передеплоя) сообщение перечитывается заново → вторая запись
   `deliveries` на тот же заказ, при том что в Kafka UI по-прежнему видно
   только 1 сообщение.

Один подготовленный fix-коммит (идемпотентность по `correlationId` +
корректный порядок коммита оффсета) — для ретеста.

## 5. Git / CI-CD структура

- `main` — чистый baseline, без багов, уже поднят к началу занятия.
- Пайплайн (GitHub Actions) триггерится на **`pull_request`** в `main`.
  Проверяет: линт (ruff/flake8) + юнит-тесты (мокают Kafka-клиент,
  проверяют только бизнес-логику — например, правила переходов статуса,
  расчёт даты доставки). **Не включает** интеграционный тест с реальной
  Kafka — намеренно, это и есть материал для разбора в конце занятия.
- Цикл на каждую ветку: push → открыт PR в `main` → зелёные чеки на
  вкладке PR **Checks** → ведущий подтягивает ветку к себе, пересобирает
  стенд → студенты тестируют через общий Swagger/Kafka UI/Kibana/DBeaver →
  находят баг(и) → ведущий пушит подготовленный fix-коммит в ту же ветку/PR
  → студенты ретестят и подтверждают, что баг(и) устранены.
- Оба PR (`feature/producer-bugs`, `feature/consumer-bug`) остаются
  зелёными на всём протяжении — именно это и демонстрирует разрыв между
  «CI прошёл» и «баг есть».

## 6. Доступ студентов

Стенд поднят на машине ведущего, наружу — через `ngrok`/`cloudflared`.
В чат даются 3 ссылки (Swagger `order-api`, Kafka UI, Kibana) + данные
подключения к Postgres для DBeaver. План Б при падении туннеля — шаринг
экрана вместо самостоятельного доступа студентов.

## 7. Границы (вне охвата этой версии)

- Реальный деплой (CD в смысле выкладки в прод) не реализуется — только CI
  часть (build+test на PR).
- Consumer lag как отдельный сценарий не включён (было решено оставить
  вне рамок 90 минут).
- Только одна когорта/один прогон — многопользовательская изоляция стенда
  (несколько параллельных студентов со своими данными) не нужна, т.к.
  стенд общий и управляется вручную ведущим.

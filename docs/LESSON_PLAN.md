## 1. Теория: Kafka (5 мин на созвоне, но держать в голове весь час)

- **Топик** — именованный поток событий одного типа. Нельзя удалить или
  изменить сообщение по ID — только дописать новое в конец.
- **Продюсер** — тот, кто пишет в топик (`order-api` в этом занятии).
- **Консьюмер** — тот, кто читает из топика (`delivery-worker`).
- **Партиция и ключ** — топик физически разбит на партиции; порядок
  сообщений гарантирован только внутри одной партиции. В стенде — по одной
  партиции на топик, поэтому порядок всегда гарантирован (на проде с
  несколькими партициями это не так автоматически).
- **At-least-once delivery** — Kafka и типичные продюсеры/консьюмеры по
  умолчанию гарантируют «доставлено минимум один раз», не «ровно один раз».
  Отсюда дубли — это не экзотика, а нормальное свойство архитектуры, если
  никто явно не построил идемпотентность поверх.
- **Consumer group и offset** — позиция консьюмера в топике (offset)
  сохраняется отдельно от самих сообщений. Если offset закоммичен неверно
  (раньше времени или не закоммичен вовсе), при рестарте консьюмер
  перечитывает уже обработанные сообщения — источник Бага 4.
- **Kafka не валидирует схему сообщений.** Что продюсер положил в топик,
  то там и лежит — консьюмеру самому решать, что делать с «плохими»
  данными. Источник Бага 2.

## 2. Что именно проверяем в Kafka — чек-лист по багам

Общий приём: **сравнить «сколько сообщений» с «сколько результата»**.

| Баг | Что видно в Kafka UI | Что видно на выходе | Вывод |
|---|---|---|---|
| Baseline | 1 сообщение | 1 запись доставки | всё ок |
| 1. Дубль (продюсер) | **2** сообщения на 1 действие | — | продюсер виноват |
| 2. Битое сообщение (продюсер) | 1 сообщение **есть** | доставки нет; в Kibana — ошибка парсинга у `delivery-worker` по `correlationId` | продюсер отправил кривые данные, консьюмер корректно не смог их обработать |
| 3. Неполный батч (продюсер) | count в топике < count в БД по статусу | ответ ручки говорит "разослано N", по факту N-1 | продюсер тихо потерял один элемент батча |
| 4. Повтор (консьюмер) | **1** сообщение | **2** записи доставки после рестарта воркера | консьюмер виноват (нет идемпотентности/оффсет) |

Правило для студентов: **если сообщений в Kafka UI меньше или равно
ожидаемому — смотреть на консьюмера; если сообщений больше или соответствие
1:1, а результат всё равно неверный/отсутствует — смотреть на то, что
реально попало в сообщение (Kafka UI → Value) и на логи консьюмера
(Kibana)**.

## 3. Теория: CI/CD

- **CI (Continuous Integration)** — автоматическая проверка кода при
  каждом изменении (здесь — при открытии PR): линт + тесты. Отвечает на
  вопрос «не сломали ли мы что-то, что уже было проверено», а не «работает
  ли фича целиком».
- **CD (Continuous Delivery/Deployment)** — автоматическая раскладка после
  CI. В этом занятии не реализуется — фокус только на CI-части.
- **Зелёный чек ≠ отсутствие багов.** Чек зелёный ровно настолько, насколько
  зелены сами тесты. Если тесты мокают Kafka и не проверяют, что реально
  происходит с топиком — они физически не могут поймать ни один из 4 багов
  этого занятия. Это главный вывод занятия для роли QA: **читать, что
  именно проверяет пайплайн, а не просто смотреть на цвет галочки**.
- **Роль QA в CI/CD** — не только гонять юнит-тесты руками, но и понимать,
  какие классы багов пайплайн в принципе не покрывает, и указывать на этот
  пробел (в идеале — предлагать, какой тест туда добавить).

## 4. Команды, которые понадобятся

**Git:**
```bash
git fetch origin
git checkout feature/producer-bugs   # или feature/consumer-bug
git pull
git log --oneline -5                 # показать студентам, что реально запушено
```

**Docker / стенд:**
```bash
docker compose up --build -d         # пересобрать и поднять после checkout
docker compose ps                    # убедиться, что всё Up/healthy
docker compose logs -f delivery-worker   # смотреть обработку в реальном времени
docker compose restart delivery-worker   # имитация передеплоя — триггер Бага 4
```

**Kafka (если нужно показать из терминала, не только через Kafka UI):**
```bash
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic order.status_changed --from-beginning

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list
```

**SQL (DBeaver) — для сверки с батчем:**
```sql
SELECT count(*) FROM orders WHERE status = 'READY_FOR_DELIVERY';
SELECT * FROM deliveries WHERE order_id = <id>;
```

**GitHub:** страница PR → вкладка **Checks** — там зелёная/красная галочка
и лог каждого шага пайплайна.

## 5. Плейбук «фикс → ретест»

### Ветка `feature/producer-bugs` (все 3 бага сразу)

1. После того как студенты нашли все 3 бага — запушить подготовленный
   fix-коммит в ту же ветку/PR.
2. Показать: CI остаётся зелёным (он и был зелёным — фикс не меняет то,
   что тесты проверяют, только реальное поведение).
3. `git pull` + `docker compose up --build -d` на стенде.
4. Ретест силами студентов:
   - Смена статуса одного заказа → в Kafka UI **1** сообщение (не 2).
   - Смена статуса на «плохой» переход → сообщение корректное, доставка
     появляется.
   - `POST /orders/dispatch-batch` → `dispatchedCount` совпадает с
     `SELECT count(*) ... WHERE status = 'READY_FOR_DELIVERY'`, и ровно
     столько же сообщений в топике `order.dispatch_requested`.

### Ветка `feature/consumer-bug`

1. Запушить fix-коммит (идемпотентность по `correlationId`).
2. CI зелёный (как и был).
3. `git pull` + `docker compose up --build -d`.
4. Ретест: сменить статус → `docker compose restart delivery-worker` →
   `GET /orders/{id}/delivery` по-прежнему показывает **1** запись, а не 2.

## 7. Если что-то пошло не так

- Туннель (ngrok/cloudflared) упал — переходим на шаринг экрана, студенты
  наблюдают, не тыкают сами.
- Стенд не поднимается — `docker compose down -v && docker compose up
  --build -d` (полный сброс), пока студенты читают теорию/`DESIGN.md`.
- Не хватает времени — первым сокращать блок 70–82 (разбор CI/CD можно
  провести короче, устно, без попытки что-то добавить в пайплайн живьём).

### `POST /admin/reset` — на что он не влияет

`/admin/reset` (только для репетиций ведущего, не для студентов) делает
`TRUNCATE ... RESTART IDENTITY CASCADE` на Postgres и пересеивает те же
данные — новые заказы после сброса снова получают ID начиная с 1. Но он
**не трогает Kafka**: топики и оффсеты консьюмер-группы не очищаются. Если
до сброса уже был тестовый прогон, в топиках остаются старые сообщения с
теми же `correlationId`, что и у свежепересеянных заказов — счётчик
«сколько сообщений в Kafka UI» после такого сброса может вводить в
заблуждение, а именно на сравнении этого счётчика с результатом и строится
вся диагностика по багам (см. раздел 2). Единственный способ получить
по-настоящему чистое состояние (без задвоенных `correlationId` в топиках)
— полный сброс стенда: `docker compose down -v && docker compose up
--build -d`, а не `/admin/reset`.

Связанный риск: повторный вызов `POST /orders/dispatch-batch` без смены
данных вернёт `dispatchedCount: N` снова, но 0 *новых* записей в
`deliveries` — это ожидаемое идемпотентное поведение, не баг. Если не
учитывать, что это повторный прогон, зелёный `dispatchedCount: N` можно
по ошибке принять за «всё окей», хотя по факту ничего нового не
произошло.

### Kibana: `app-logs-*` data view после `down -v`

`docker compose down -v` удаляет volume Elasticsearch — вместе с данными
пропадает и сохранённый в Kibana data view `app-logs-*`. Filebeat поднят
с `setup.template.enabled: false`, поэтому ничего не создаёт data view
автоматически — это верно и для самого первого чистого запуска стенда, не
только после `down -v`. После любого `down -v` (и на первом запуске)
нужно вручную создать его в Kibana: **Stack Management → Data Views →
Create data view**, index pattern `app-logs-*`, time field `@timestamp`.
